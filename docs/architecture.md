# Архитектура

## Контуры приложения

`main.py` создаёт SQLite-хранилище, корневой `App`, aiohttp-приложение и слушающий HTTP-сокет. Затем `App.start()` восстанавливает настроенные Telegram-клиенты и запускает планировщик. Отдельный веб-сервер, брокер очередей, Docker, Redis или cron для штатной работы не требуются. Запускать несколько копий приложения с одной базой нельзя: восстановление прерванных операций рассчитано на один процесс, а блокировки задач находятся в памяти.

```text
                       пароль / cookie / X-Panel
                               │
              static/index.html ↔ web.py
                               │ workspace_id запроса
                    App ↔ WorkspaceApp
                 ┌─────────────┼─────────────────┐
                 │             │                 │
         collector / LLM    модули         PlanEngine
                 │             │                 │
           черновики     очередь / фото    статья + сценарий
                 │             │                 │
                 └── модерация ┘       Pillow → FFmpeg → ffprobe
                          │                      │
                  общий Telegram-бот ←───────────┘
                          │
                 сохранённый канал назначения

  DB + workspace_sql: общая SQLite, раздельные редакционные записи
  cycle_cost: отчёты циклов и инструментированных LLM-операций
```

## Общие подключения и раздельные данные

Все редакционные пространства используют **один аккаунт-читатель, один бот и общие подключения провайдеров**. Источник может независимо присутствовать в нескольких пространствах: включение, удаление, курсор чтения и обработка в одном не изменяют другой.

| Область | Что хранится |
| --- | --- |
| Глобальные настройки `settings` | Telegram API ID/hash, reader/bot StringSession, телефон, токен бота, администраторы и код привязки; news LLM provider/base URL/key; plan provider/key; служебный пароль при автогенерации |
| `workspace_settings` | Модель и тарифы новостей, персона и инструкции, язык и длина, параметры прогноза, источники редакционного поведения, канал публикации, подпись, расписание, флаги модулей; модель/тарифы/пауза/длина контент-плана |
| `channels`, `posts` | Состав источников, курсоры и оригиналы; составные ключи включают `workspace_id` |
| `proposals` | Черновик, исходная версия текста, ссылки на сохранённые источники, статус, тип, назначения, ссылки на management-карточки |
| `events`, `collection_cycles`, `llm_operations` | События и сохранённые отчёты с владельцем `workspace_id` |
| `content_plan` | Темы, заметки, даты, payload, связь с черновиком/расходом, состояние подготовки и подтверждения отправки |

Глобальные ключи перечислены в `db.GLOBAL_KEYS`. Workspace выбирается по `X-Workspace-ID` либо параметру `workspace_id`; отсутствие обоих означает пространство `1`. Несовпадающие указания отвергаются. `WorkspaceApp`/`DB.workspace()` дают фиксированные представления, а не переключают процессную «текущую вкладку».

`workspace_sql.ScopedConnection` адаптирует фиксированный набор SQL-запросов новостной части. Это не универсальный SQL-анализатор и не отдельная база на клиента. Новые запросы требуют регрессионной проверки изоляции. `PlanStore` использует явные условия `workspace_id` в собственных SQL-запросах.

При миграции старые записи принадлежат «Основной», существующие назначения сохраняются в черновиках. Новые области не получают чужие источники/канал/модель: новости на паузе, автопубликация выключена, план пуст и на паузе. Доступ всех администраторов общий — workspace не является ACL.

## Обычные новости

1. `collector.collect()` читает включённые Telegram-источники через Telethon. При первом чтении рассматриваются не более `20` последних сообщений не старше `24` часов; далее используется `last_id`. Пропускаются тексты короче `40` символов и сообщения со стоп-словами. Сохраняется текст, ограниченный `max_chars`, ссылка и наличие фото.
2. Цикл берёт до `max_posts` сохранённых необработанных сообщений. `llm.propose()` передаёт их модели вместе с недавними заголовками. Отбор событий и объединение фактов выполняет модель — это не независимый поисковый fact-checker.
3. `prompts` собирает редакционный шаблон, характер, добавки включённых модулей и финальные обязательные правила структуры, темы тегов и прогноза. Логический запрос один; явные сетевые повторы и fallback из неподдерживаемого JSON-режима могут увеличить число HTTP-вызовов.
4. Финальные инструкции задают выбранный горизонт. `news_outlook` проверяет осторожность последствий, допущения, неопределённость и длину. При отсутствующем, небезопасном или некорректном ответе используется короткий общий редакционный шаблон возможных последствий с выбранным горизонтом, без новых фактов и уверенности в исходе; его текст отмечен как «Редакционный сценарий». Включённый прогноз не заменяется служебным сообщением об ошибке или отказом; нормальный сценарий — вывод, написанный моделью. При выключенном прогнозе в новом результате убирается и помеченный прогноз, ошибочно возвращённый моделью. Сохранённые старые тексты и ручные правки автоматически не меняются.
5. Создаётся `proposal` с типом `normal` или `breaking` и снимком канала назначения. Успешно обработанный пакет отмечается использованным; автоматический anti-repeat по заголовкам — инструкция модели, а не семантическая гарантия отсутствия дублей.
6. `deliver()` отправляет карточки администраторам либо запускает явно включённую автопубликацию. `approve()` может поставить обычный черновик в очередь; `publish()` отправляет в сохранённый канал.

Статусы обычного черновика: `new`, `queued`, `published`, `skipped`. Все пути принятия/отклонения используют общую блокировку решения для ID черновика. Telegram-кнопки и правка reply определяют пространство по самому черновику, не по открытой вкладке панели.

После принятия в очередь, публикации или отклонения удаляются **только сохранённые ссылки на management-карточки бота**. Неудачные удаления остаются для прицельного повторения; ошибка уборки не отменяет успешную отправку. История в панели сохраняется. Массового удаления прошлых сообщений при старте нет.

## Форматирование и два вида хэштегов

Модель пишет обычный текст с ограниченным синтаксисом `**жирное**`. `post_format.py` превращает допустимые выделения в контролируемые HTML-теги и экранирует произвольный HTML. Для старых обычных текстов возможна детерминированная подача заголовка/абзацев без нового LLM-вызова и без перезаписи базы.

`App.channel_html()` резервирует место под подпись, источники и тематическую строку, учитывает видимую длину в UTF-16: `4096` для сообщения, `1024` для подписи. Не следует рассчитывать, что любая модель точно соблюдает желаемую длину или число тегов.

- **Тематические теги** принадлежат конкретной статье. Финальные инструкции запрашивают `3–5` релевантных тегов; локальный форматтер сохраняет и нормализует существующую завершающую строку, но не придумывает темы за модель.
- **Служебные метки** принадлежат management-карточке. Исторические ключи `publication_hashtags` и `publication_hashtags_enabled` теперь управляют только меткой пространства. Пустое значение означает имя пространства, выключатель убирает метку. В канал она не дописывается.

## Модули новостей

Все поставляемые модули по умолчанию выключены. Настройки `mod.<id>.*` принадлежат выбранному workspace.

| Модуль | Механизм и ограничения |
| --- | --- |
| `media` | Фото из сохранённого источника, скачивание читателем, кэш в `media/workspace-<id>/` рядом с БД. Длинная подпись: текст без фото либо фото и отдельное сообщение. Это не генерация изображений. |
| `queue` | Одобренные новости выпускаются по слотам; число постов на слот и уведомления настраиваются. После перерыва слот ловится в окне `15` минут. Есть немедленная отправка, перестановка и возврат из очереди. |
| `learning` | Примеры опубликованных/исправленных текстов и отклонённые темы добавляются в промпт. Веса модели не обучаются; это few-shot/context, не fine-tuning. |
| `breaking` | Периодический сбор и эвристические кластеры общих слов из разных каналов. Возможны ложные совпадения. Срочная автопубликация — отдельный выключенный по умолчанию флаг, обходящий очередь и модерацию. |

Основной scheduler вызывает модули только для неприостановленных пространств. «Тихие часы» блокируют плановый новостной сбор; не являются общим запретом всех публикаций: очередь и контент-план имеют свои правила, срочный модуль — настройку ночной работы.

## Контент-план и MP4

План не требует читателя и списка источников. Тема/заметки владельца — материал, а не подтверждение актуальных фактов. Задание сохраняет назначение при создании, а не берёт текущий канал заново перед отправкой. Общий провайдер использует `plan_model` или news-модель; native Anthropic требует отдельные глобальные ключ и выбор провайдера, а также workspace-модель.

Один ответ содержит статью и строгий сценарий: `3–5` сцен с заголовком, текстом, иконкой из разрешённого списка и `2–4` шагами. При выключенном видео сценарий может быть пустым. Нет второго запроса для сценария, выполнения кода, скачивания модельных URL или универсальной text-to-video модели. План использует собственный фиксированный образовательный промпт, тему/заметки, язык, эмодзи и правила оформления; полный новостной пользовательский промпт и persona не следует считать автоматически унаследованными.

`motion_renderer.py` рисует кадры Pillow, передаёт raw RGB в локальный FFmpeg и проверяет результат ffprobe. Формат: `720×1280`, `24 fps`, H.264/yuv420p, без аудио; длительность для `3/4/5` сцен — `21/24/30` секунд. Единственная реализованная тема рендера — `tech`; это не переключатель нескольких художественных стилей. Есть ограничения размера, времени, схемы, файловых путей и параллельности.

Артефакты лежат в `content-plan/workspace-<id>/item-<id>/motion.mp4` рядом с БД. Директории закрыты `0700`, файл `0600`, окончательная замена атомарна после проверки. API видео проверяет сессию и workspace.

```text
scheduled → generating → [rendering] → ready → publishing → published
                  ↘ error / interrupted      ↘ uncertain
scheduled / ready → missed        допустимые непубликуемые → cancelled
```

Автоматическое окно исполнения — до `15` минут после назначенного срока. Пропущенные задания получают `missed`, а не публикуются массово задним числом. Если текст не помещается в видеоподпись, видео отправляется с кратким заголовком, статья — отдельным reply. Подтверждённые ID видео/текста и фаза отправки сохраняются. Неоднозначная отправка получает `uncertain`; автоматический повтор запрещён. План имеет последовательный слот подготовки, а не неограниченный параллельный рендер.

## Расходы и история

`cycle_cost.py` привязывает явные попытки completion к текущей операции и задаче. Обычные сборы сохраняются в `collection_cycles`, генерация характера и подготовка плана — в `llm_operations`. В отчётах — счётчики/usage, источники суммы, тарифный снимок, статус и признаки полноты, не промпты и не тела ответов.

Приоритет имеет сообщённая провайдером сумма, когда поддерживается; иначе — оценка по заданным USD-тарифам за миллион входных/выходных токенов. Неизвестная usage, тариф, cache pricing или оборванный запрос не превращаются в нулевой расход. Локальный режим без счёта требует явного подтверждения и loopback-провайдера. Реальных цен система не угадывает.

`DB.recorded_spending()` складывает известные суммы сохранённых отчётов один раз по workspace и отдельно сообщает неполные записи. Переписывания, тесты подключения и самостоятельные запросы модулей вне инструментированного цикла нельзя считать полностью покрытыми этим учётом. Удаление отчётов меняет показанную сумму, а не счёт внешнего провайдера.

## Карта исходников

| Файл | Ответственность |
| --- | --- |
| `config.py`, `main.py` | `.env`, пути/часовой пояс, старт процесса |
| `core.py`, `collector.py`, `tgbot.py` | Общие клиенты, редакционные действия, сбор, команды/кнопки |
| `db.py`, `workspace_sql.py` | Схема, миграции, изоляция новостной части, отчёты |
| `web.py`, `static/index.html` | Сессии, API, одностраничная панель |
| `settings.py`, `prompts.py`, `llm.py`, `news_outlook.py` | Валидация, редакционный контракт, completion, условный прогноз |
| `post_format.py`, `qr_login.py` | Безопасная подача текста; ограниченный вход по QR |
| `content_plan.py`, `plan_store.py`, `plan_llm.py`, `motion_renderer.py` | Независимый план, durable-состояние, статья/сценарий, CPU-рендер |
| `cycle_cost.py`, `modules/` | Записанные расходы и дополнительные функции |
| `tests/` | Офлайн-регрессии, UI-fixtures, проверки рендера |

Описание опирается на указанные функции и структуры кода. Новые `news_outlook_*` настройки описаны по контракту интерфейса и должны проверяться вместе с backend/UI соответствующего релиза.
