# Эксплуатация и восстановление

## Проверки без генерации

Для собственного развёртывания с примерным unit:

```bash
sudo systemctl status content-gen.service --no-pager
sudo systemctl show content-gen.service -p ActiveState -p MainPID -p NRestarts
curl --fail http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/api/state
sudo journalctl -u content-gen.service -n 30 --no-pager
```

Ожидается работающий процесс без restart-loop, `ok` у health и `401` у API без входа. Журнал просматривайте локально; перед передачей удаляйте пароли, токены, номера, адреса назначения, ссылки привязки, исходное частное содержимое и исключения, которые могут его содержать. Не печатайте окружение процесса или всю таблицу `settings` для диагностики.

В защищённой панели проверьте выбранный workspace, подключения, паузу, обычную/срочную автопубликацию, независимую паузу плана, назначение и стоимость последней операции. HTTP-health не удостоверяет Telegram-подключение, ответ LLM или реальную публикацию.

**Не создавайте второй обычный `DB()` или `App()` над действующей базой для read-only проверки.** Инициализация выполняет миграции, завершает сохранённые running-операции как interrupted и обновляет служебное состояние. Для инспекции нужна SQLite URI `mode=ro` и `PRAGMA query_only=ON`, без App/DB-конструкторов.

## Паузы не взаимозаменяемы

| Действие | Что останавливается | Что не следует считать остановленным |
| --- | --- | --- |
| Пауза новостей | Плановый сбор, автоматические тики news-модулей/очереди выбранного workspace | Ручной сбор/переписывание, прямое решение о публикации, контент-план |
| Тихие часы | Плановый обычный сбор; срочный модуль учитывает отдельный `at_night` | Очередь, контент-план, ручные действия |
| Пауза плана | Новые автоматические задания/автоматическая отправка плана | Уже начатая подготовка, ручная подготовка/ранняя публикация |
| Остановка сервиса | Данный процесс целиком | Уже принятая Telegram отправка или уже выполненный платный API-запрос |

При обслуживании сначала проверьте текущие операции/готовые задания, согласуйте остановку и сохраните данные. Рестарт может прервать preparation или отправку; не превращайте неопределённость в автоматический повтор.

## История, очистка и хранение

- После новостного цикла очищаются использованные оригиналы старше `14` дней, кроме нужных ещё открытым/queued-предложениям; журнал ограничивается последними `500` событиями в области. Источники старой опубликованной статьи могут перестать быть доступны через локальную историю.
- Медиа-модуль при активных тиках примерно раз в сутки удаляет обычные файлы выбранного workspace-кэша старше `14` дней. Он не обходит чужие workspace-каталоги, symlink или директории. Счётчик отсутствующего кэша возвращает ноль без создания папки.
- Черновики и история решений не удаляются только потому, что management-карточка исчезла в Telegram. Удаляются только записанные карточки управления, не сообщения канала.
- Нет заявленной автоматической политики удаления MP4 контент-плана или всех отчётов расходов по сроку. Учитывайте место на диске; удаление артефакта означает потерю локального просмотра/готовности, а не откат публикации.
- Перезапуск переводит `generating/rendering` плана в `interrupted`, а `publishing` — в `uncertain`. Сохранённые running-отчёты расходов становятся неполными/interrupted; стоимость оборванного запроса нельзя считать нулевой.

## Резервная копия перед изменением

Риск: неполная копия SQLite или откат старой БД потеряет решения/подтверждения отправки и может привести к дублям; восстановление выполняйте на согласованную точку, с проверкой канала и последующих данных.

Сохраняйте:

1. Версию/commit исходников, dependency-файлы, проверенный unit и конфигурацию proxy.
2. Защищённую startup-конфигурацию отдельно от Git.
3. **Согласованную** SQLite backup-копию, не blind `cp` активного файла.
4. Нужные MP4/медиа рядом с БД, если необходима возможность просмотра/повторной подготовки. Транзакционная SQLite-копия сама не делает файловые артефакты согласованным snapshot.

Пример **ручной остановленной** SQLite-копии для пути из systemd-шаблона. Целевой backup-каталог условный, закрытый, вне репозитория. Не запускайте этот блок без согласования обслуживания:

```bash
sudo systemctl stop content-gen.service
sudo install -d -o root -g root -m 700 /var/backups/content-gen
sudo /opt/newsbot/.venv/bin/python -I - <<'PY'
import os
import sqlite3
from datetime import datetime, timezone
from pathlib import Path
os.umask(0o077)
source = Path('/var/lib/content-gen/newsbot.db')
target = Path('/var/backups/content-gen') / (
    'newsbot-' + datetime.now(timezone.utc).strftime('%Y%m%dT%H%M%S%fZ') + '.sqlite'
)
# Exclusive reservation prevents accidental replacement of an earlier backup.
fd = os.open(target, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
os.close(fd)
src = sqlite3.connect(source.as_uri() + '?mode=ro', uri=True)
src.execute('PRAGMA query_only=ON')
dst = sqlite3.connect(target)
try:
    src.backup(dst)
    result = dst.execute('PRAGMA integrity_check').fetchone()[0]
    if result != 'ok':
        raise RuntimeError('Backup integrity check failed')
finally:
    dst.close()
    src.close()
print('SQLite backup integrity: ok')
PY
# Продолжайте обслуживание или запустите сервис после проверки.
sudo systemctl start content-gen.service
```

Это пример backup API, а не проверенный backup ваших данных. При ошибке не продолжайте установку: сохраните прежние данные, разберитесь с ошибкой и восстановите сервис по согласованному плану. Backup содержит действующие сессии/ключи; ограничивайте доступ, храните защищённо и проверяйте восстановление на отдельной копии без сети/Telegram.

## Обновление и откат

1. Подготовьте проверенный checkout и зависимости отдельно; выполните офлайн-тесты, просмотр diff и проверку секретов.
2. Зафиксируйте текущие паузы, подключения, назначения и состояние плана без выгрузки секретов. Согласуйте остановку.
3. Остановите **только свой** content-gen сервис, сделайте согласованный backup и копии заменяемых файлов/конфигурации.
4. Установите проверенные исходники, не перезаписывая `.env`/panel.env и данные. Миграции выполняются при старте; обслуживание БД отдельно требует понимания их состава.
5. Запустите сервис, проверьте integrity на read-only соединении, установленную версию, health, защиту API, права runtime и неизменность намеренных настроек. Сверьте exact UI/маршруты QR/MP4, если менялся proxy-prefix.
6. Живые QR/LLM/Telegram проверки оставьте отдельным явным решением оператора. Не запускайте платный сбор «для доказательства установки» автоматически.

Возврат старого монолитного кода поверх multi-workspace БД может нарушить изоляцию. Предпочтителен forward-fix либо совместимый исходный релиз. Восстановление старой БД может потерять новые публикации, очереди, курсоры, расходы и отправочные ID; нельзя заменять её молча ради совпадения прежних настроек. При откате сохраните текущее состояние и оцените изменения с момента backup.

## Повторный анализ

В обзоре можно вернуть в обработку **сохранённые** исходные сообщения за час, сутки или весь доступный период. Операция меняет `used=1 → 0` с включительной границей `date>=cutoff` и требует паузы новостей/свободной collection-lock.

Она **не** восстанавливает уже очищенные оригиналы, не сбрасывает channel cursor, не удаляет предложения/anti-repeat-заголовки и отчёты, не запускает платный цикл сама. Следующий явный сбор может вызвать новый LLM-запрос. Если модель продолжает учитывать прежние темы, повторный анализ не гарантирует повторного предложения той же новости.

## Сброс тестового новостного содержимого

Деструктивная операция отделена от reanalysis: сначала preview количества, затем точное подтверждение `СБРОС`. Нужны paused-news и свободная collection-lock. Действие ограничено выбранным workspace.

Удаляются `posts`, `events`, `collection_cycles` и **неплановые** `proposals`; сбрасываются курсоры/результаты fetch и `last_run/last_result`. Сохраняются каналы, credentials/sessions, остальные настройки, схема, `llm_operations`, durable `content_plan` и связанные planned-черновики/отправочные данные.

Не удаляются сообщения Telegram, файлы медиа и MP4 на сервере. Сброс исторических отчётов уменьшает отображаемую известную сумму, но не реальный счёт провайдера. После снятия паузы источники читаются заново по первому fetch-окну, а не за всё время. Из-за сброса курсоров возможно повторное появление уже знакомых событий; сначала проверьте последствия.

Этот контроль называется «тестовым», но не умеет автоматически распознавать, какие записи были настоящими: он удаляет всё содержимое указанных новостных таблиц выбранной области. Наличие кнопки не является разрешением на выполнение.

## Когда отправка неоднозначна

Для ordinary-news после transport-сбоя сверяйте фактический канал; не утверждайте, что сообщение не отправилось только из-за исключения. Для плана смотрите `uncertain` и сохранённые подтверждения видео/текста; ошибку нельзя исправлять слепым retry или сменой назначения. Ручное согласование результата и любых повторных отправок — обязанность оператора, автоматического полноценного reconciliation-интерфейса не заявлено.
